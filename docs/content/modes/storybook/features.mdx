# Writing features

## Feature files become stories

Keep your feature files where you like:

- **next to their stories files**, as Storybook keeps a component's files together: a feature file
  uses the stories file next to it with its name, `X.stories.<ext>` for `X.feature` (or
  `X.feature.md`), with nothing more to write;
- **in `features/`**, as Cucumber projects keep them (`features/**/*.feature`): each feature names
  its stories file with a [stories file step](#storybook-steps)
  (`Given the stories of src/stories/Greeting.stories.ts`).

Both work in one project: the pattern in Storybook's [`stories`](/modes/storybook#add-the-addon)
lists both folders (`"../@(src|features)/**/*.@(feature|feature.md)"`). The examples here keep the
feature next to its stories file:

A feature file next to a stories file but named another way needs the stories file step too
(`X.stories.feature` as well: it isn't taken as `X.stories.<ext>`'s).

Each scenario's story:

- **renders the story its Storybook step names** (`Given the Ada story`), with everything the
  story has (`args`, `render`, `decorators`, `parameters`, …) but its own `play`, which the scenario
  replaces; with `default`, or no story step, it renders the stories file's meta (its `component`,
  `args`, `render`, …);
- **uses the stories file's meta**: its decorators, loaders, parameters and tags, as any story of
  that file;
- is **named after the scenario** (an Outline row after its row), with the story's tags and the
  scenario's Gherkin tags (with their `@`), and not in autodocs pages;
- is listed under **the stories file's title, then the feature**: `Example/Greeting/Feature: Greeting`
  (the title written in the stories file, or Storybook's automatic one if it writes none; then the
  feature's keyword and name; a feature without a name, its file's name without the extension:
  `Feature:` in `Greeting.feature` is `Feature: Greeting`). Several features on one stories file are
  told apart by their names: give each its own. A `/` in a feature's name is listed as a `|`
  (`Feature: Log in/out` as `Feature: Log in|out`): Storybook splits a title at each `/`.
  How the sidebar shows it: [Running](/modes/storybook/running#in-storybooks-ui).

The stories file's own stories stay ordinary stories, listed under its title.

```gherkin filename="src/stories/Greeting.feature"
Feature: Greeting

  @smoke
  Scenario: Saying hello
    Given the Ada story
    When I click the "Say hello" button
    Then I see the text "Hello, Ada!"

  Scenario Outline: Greeting <name>
    Given the <name> story
    When I click the "Say hello" button
    Then I see the text "Hello, <name>!"

    Examples:
      | name  |
      | Ada   |
      | Grace |

  Scenario: Greeting the world
    Given the Basic story
    When I click the "Say hello" button
    Then I see the text "Hello, World!"
    And its "onGreet" handler was called
```

```ts filename="src/stories/Greeting.stories.ts"
import type { Meta, StoryObj } from "@storybook/react-vite";
import { fn } from "storybook/test";
import { Greeting } from "./Greeting";

const meta = {
  title: "Example/Greeting",
  component: Greeting,
  args: { name: "World", onGreet: fn() },
} satisfies Meta<typeof Greeting>;

export default meta;
type Story = StoryObj<typeof meta>;

// "Saying hello" and the Outline's first row render it, with these args;
// the tags of "Saying hello" are ["people", "@smoke"]
export const Ada: Story = {
  tags: ["people"],
  args: { name: "Ada" },
};

// The Outline's second row
export const Grace: Story = {
  args: { name: "Grace" },
};

// "Greeting the world": the meta's args as they are
export const Basic: Story = {};
```

The Outline gives each row its own story with a column (`<name>`).

The story step is optional: a scenario without one renders the stories file's meta (its `component`
with its `args`). `Given the default story` says the same explicitly, for a stories file that has
only a meta. `default`, in lowercase, is the meta: not a story named `Default`.

## Storybook steps

The Storybook steps are ordinary step definitions of yours, worded as you like, with one of the
plugin's parameter types in their expression. The plugin defines those types itself, in Storybook
only, when it finds a Storybook step in your support files. Their code does nothing: the plugin
reads the expressions to link each scenario before anything runs.

```ts filename="features/steps/stories.ts"
import { Given } from "@cucumber/cucumber";

Given("the {storybook:story} story", (_story: string) => {});
Given("the unmounted {storybook:storyUnmounted} story", (_story: string) => {});
Given("the stories of {storybook:storiesFile}", (_file: string) => {});
```

| Parameter type | Matches | Links |
| --- | --- | --- |
| `{storybook:story}` | an export name (`\w+`), or `default` for the meta | the scenario to that story, rendered before the steps |
| `{storybook:storyUnmounted}` | an export name (`\w+`), or `default` for the meta | the scenario to that story, not rendered: a step mounts it |
| `{storybook:storiesFile}` | a path (`\S+`) | the feature to that stories file, instead of the one next to it |

- **Don't define these parameter types yourself**: the plugin does, and a type you define under
  one of these names is used as you defined it.
- **Keep the Storybook steps where only Storybook's `import` globs load them**: a node or browser
  project doesn't have these parameter types, so a step using one is an undefined parameter type
  there and its scenarios fail.
- **Write each expression as a string literal**, directly as the first argument of `Given`, `When`,
  `Then` or `defineStep`, in a file of `import`: the plugin finds them in your support files without
  running them. A Storybook step anywhere else (in a module a support file imports) isn't found:
  it links nothing, and if it's the only one its parameter type is undefined. One of the plugin's
  parameter types per step definition; cucumber's built-in ones (`{string}`, `{int}`, …) are fine
  beside it, your own aren't.
- **A scenario names at most one story** and one stories file. A Background's Storybook step
  applies to each scenario it runs before.
- **The stories file step** names one stories file for the whole feature, from anywhere in it:
  relative to the feature with `./` or `../`, else from the project's root
  (`Given the stories of src/stories/Greeting.stories.ts`).

A link the plugin can't make is an error, with every such error of the feature listed: a story the
stories file doesn't have (its stories listed), a story named with no stories file, a missing stories
file, two stories files in one feature, two stories named in one scenario, a step two Storybook
steps match. Each one, and what to do:
[Troubleshooting](/guides/troubleshooting#a-feature-that-cant-be-linked).

## Mounting

A scenario's story is rendered before its steps, as Storybook renders a story before its `play`. A
scenario on an unmounted story (`Given the unmounted ThePage story`) isn't: a step of yours mounts
it, after any setup before it:

```gherkin
Scenario: Unmounted
  Given the unmounted ThePage story
  Given the API answers with an error
  When I mount the story
  Then I see the error message
```

```ts filename="features/steps/stories.ts"
import { When } from "@cucumber/cucumber";
import type { StoryWorld } from "../support/world.ts";

When("I mount the story", async function (this: StoryWorld) {
  await this.story.mount();
});
```

The plugin never mounts an unmounted story itself. In Storybook's UI, a story that ends without being
mounted fails (Storybook's `NoStoryMountedError`).

## Steps for stories

Steps use the running story's context, from `story()`. Give your World a getter for it:

```ts filename="features/support/world.ts"
import { setWorldConstructor, World } from "@cucumber/cucumber";
import { story } from "@lotun/vitest-cucumber/storybook";
import type { StoryContext } from "@storybook/react-vite";

export class StoryWorld extends World {
  get story() {
    return story<StoryContext>();
  }
}

setWorldConstructor(StoryWorld);
```

```ts filename="features/steps/stories.ts"
import { Then, When } from "@cucumber/cucumber";
import { expect } from "storybook/test";
import type { StoryWorld } from "../support/world.ts";

When("I click the {string} button", async function (this: StoryWorld, name: string) {
  const { canvas, userEvent } = this.story;
  await userEvent.click(canvas.getByRole("button", { name }));
});

Then("I see the text {string}", async function (this: StoryWorld, text: string) {
  await expect(this.story.canvas.getByText(text)).toBeVisible();
});

Then("its {string} handler was called", async function (this: StoryWorld, handler: string) {
  await expect(this.story.args[handler]).toHaveBeenCalled();
});
```

- Use a getter, not a field set in the constructor: it reads the story when the step runs.
- Import `expect`, `fn` and `userEvent` from `storybook/test`, not from Vitest: the same steps run in
  Storybook's UI, where there is no Vitest.
- Keep these steps in their own folder if node or browser projects share your `import` globs.

## Stories files a feature can use

A feature's stories file is read as Storybook reads CSF, without running it, so it must be **CSF 3
in JavaScript or TypeScript** (`.js`, `.jsx`, `.mjs`, `.ts`, `.tsx`, `.mts`, …):

- **CSF factories** (`meta.story()`, experimental in Storybook 10) aren't supported yet: a feature on
  such a file fails with an error saying so.
- **Svelte CSF** (`.stories.svelte`) and **Vue SFC stories** (`.stories.vue`) aren't JavaScript until
  their addon compiles them. Write the feature's stories file as `X.stories.ts` with your component
  as `component`: Svelte and Vue components work as usual.
- **MDX** files are docs, with no stories to play.

Write a story's `tags` and the meta's `title` and `tags` as literals. A stories file without a
`title` has Storybook's automatic one, and its features are listed under that. Storybook makes one
only for a file its `stories` patterns match: a stories file they don't list needs a written `title`.
