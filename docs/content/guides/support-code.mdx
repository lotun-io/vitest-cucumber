# Support code

Your step definitions, hooks, World and parameter types use
[`@cucumber/cucumber`](https://github.com/cucumber/cucumber-js)'s API, unchanged. The plugin adds
one thing to it: an arrow function can take [the World as an argument](#the-world-in-an-arrow-function).
The plugin loads the files the [`import`](/reference/options#import) option lists, in every mode.
They can be TypeScript (or TSX): Vite transforms them, with no loader or `requireModule` to set up.

## What works

| Cucumber API | Node | Browser | Storybook |
| --- | :-: | :-: | :-: |
| `Given` / `When` / `Then` / `defineStep` (Cucumber expressions, regular expressions) | ✅ | ✅ | ✅ |
| `Before` / `After` / `BeforeStep` / `AfterStep` (tags, names, timeouts) | ✅ | ✅ | ✅ |
| `BeforeAll` / `AfterAll` | ✅ | ✅ | ✅ |
| `setWorldConstructor` / `World` | ✅ | ✅ | ✅ |
| `world` / `context` / `version` | ✅ | ✅ | ✅ |
| [The World as an arrow function's first argument](#the-world-in-an-arrow-function) (the plugin's own) | ✅ | ✅ | ✅ |
| `defineParameterType` (incl. async transformers) | ✅ | ✅ | ✅ |
| `DataTable` / doc strings / `Status` | ✅ | ✅ | ✅ |
| Async, promise-returning and callback (`done`) steps and hooks | ✅ | ✅ | ✅ |
| `return "pending"` / `return "skipped"` | ✅ | ✅ | ✅ |
| A definition's `{ timeout }` | ✅ | ✅ | ✅ |
| `wrapPromiseWithTimeout` | ✅ | ✅ | ✅ |
| `setDefinitionFunctionWrapper` | ✅ | ✅ | ✅ |
| `this.attach` / `this.log` / `this.link` | ✅ | ⚠️ | ⚠️ |
| `setDefaultTimeout` | 🔀 | 🔀 | 🔀 |
| `BeforeAll` / `AfterAll` with `on: "COORDINATOR"` | 🔀 | 🔀 | 🔀 |
| `@cucumber/cucumber/api`, formatter classes | ✅ | ❌ | ❌ |
| `setParallelCanAssign` | ❌ | ❌ | ❌ |

- ⚠️ **Attachments in a page** are strings only: [Attachments](#attachments).
- 🔀 **Not supported, use Vitest's alternative**: `testTimeout` and `hookTimeout` (or a definition's
  [`timeout`](#timeouts)) for `setDefaultTimeout`, [`globalSetup`](https://vitest.dev/config/globalsetup)
  for a once-per-run `BeforeAll`/`AfterAll`.
- ❌ **Not supported.**

What isn't supported fails where it's used, with the plugin's error:
[Limitations](/reference/limitations).

## World

Each scenario gets a new World: `this` in its steps and its `Before`/`After`/`BeforeStep`/`AfterStep`
hooks. A `function` gets it as `this`. An arrow function has no `this`: it takes the World
[as an argument](#the-world-in-an-arrow-function).

```ts filename="features/support/world.ts"
import { setWorldConstructor, World, type IWorldOptions } from "@cucumber/cucumber";

export class CartWorld extends World<{ currency: string }> {
  items: string[] = [];

  constructor(options: IWorldOptions<{ currency: string }>) {
    super(options); // gives this.attach, this.log, this.link, this.parameters
  }
}

setWorldConstructor(CartWorld);
```

A World constructor that throws fails every scenario.

### The World in an arrow function

An arrow function whose first parameter is named `world` gets the World as that argument, before
the arguments Cucumber gives it. This is the plugin's own addition: Cucumber itself doesn't run
such a function.

```ts filename="features/steps/cart.ts"
import { After, Before, Given, When, type DataTable } from "@cucumber/cucumber";
import type { CartWorld } from "../support/world.ts";

Given("a cart with {string}", (world: CartWorld, item: string) => {
  world.items.push(item);
});

When("I add:", async (world: CartWorld, table: DataTable) => {
  world.items.push(...table.raw().flat());
});

Before((world: CartWorld, { pickle }) => {
  world.log(`starting ${pickle.name}`);
});

After({ tags: "@with-apples" }, (world: CartWorld) => {
  world.items = [];
});
```

- **The name is the sign.** The parameter must be named `world`. Any other function is called as
  Cucumber calls it: a `function`, an arrow function with another first parameter
  (`(item, done) => …` still gets Cucumber's callback), one that destructures it (`({ items }) => …`).
- **The rest is Cucumber's.** After the World come the step's arguments, its data table or doc
  string, and Cucumber's callback if the function takes one more. The number of arguments is
  checked as Cucumber checks it, the World counted.
- **`BeforeAll` and `AfterAll`** have no World. Their `this` is their context (`{ parameters }`),
  which an arrow function gets as a first parameter named `context`:

  ```ts
  import { BeforeAll, type IContext } from "@cucumber/cucumber";

  BeforeAll((context: IContext) => {
    context.parameters.startedAt = Date.now();
  });
  ```

Cucumber's own `world` and `context` exports work in arrow functions too
(`import { world } from "@cucumber/cucumber"`), typed as Cucumber's `IWorld`.

#### TypeScript

Annotate the argument with your World's type (`world: CartWorld`). Steps then typecheck as they
are. Hooks need the plugin's types, which type Cucumber's hooks for this form too:

- If the same `tsconfig.json` checks your `vitest.config.ts` (or `.storybook/main.ts`) and your
  support code, TypeScript already has them: the config imports the plugin.
- If not (config files checked by a `tsconfig.node.json` of their own, for example), add them to
  the one that checks your support code:

  ```json filename="tsconfig.json"
  {
    "compilerOptions": {
      "types": ["@lotun/vitest-cucumber"]
    }
  }
  ```

Without the annotation, TypeScript reads a hook's first argument as Cucumber's hook parameter.

## World parameters

`worldParameters` in the plugin's options are each World's `this.parameters`, a fresh copy per
scenario:

```ts filename="vitest.config.ts"
cucumber({
  import: ["features/**/*.ts"],
  worldParameters: { baseUrl: "http://localhost:3000" },
}),
```

They go through JSON: a value JSON can't hold fails every feature file (a `BigInt`, a cycle), and one
it changes arrives changed (a `Date` as a string, a `Map` as `{}`). To share such values, set them on
`this.parameters` in a `BeforeAll`: every World of that worker gets a copy.

## Hooks

`Before` and `After` run around each scenario, `BeforeStep` and `AfterStep` around each step, with
the scenario's World as `this` (or as [an arrow function's `world`](#the-world-in-an-arrow-function)).
With `tags`, only for the scenarios that match:

```ts filename="features/support/hooks.ts"
import { After, Before } from "@cucumber/cucumber";
import type { CartWorld } from "./world.ts";

// Only for scenarios tagged @with-apples
Before({ tags: "@with-apples" }, function (this: CartWorld) {
  this.items = ["apples"];
});

After(function (this: CartWorld) {
  this.log(`${this.items.length} items`);
});
```

## BeforeAll and AfterAll

They run once per Vitest worker (a page in browser mode): `BeforeAll` before the worker's first
scenario, `AfterAll` when the worker is done.

- With Vitest's default [`isolate: true`](https://vitest.dev/config/isolate), every feature file
  has a fresh worker: they run once **per feature file**.
- With `isolate: false`, a worker loads your support code once and runs them once for all the files
  it runs.

```ts
test: { include: ["features/**/*.feature"], isolate: false },
```

A failing `BeforeAll` skips the worker's scenarios and fails the run; a failing `AfterAll` fails the
run.

<Callout type="warning">
  For setup once per whole run (a database, a server), use Vitest's
  [`globalSetup`](https://vitest.dev/config/globalsetup): Cucumber's once-per-run hooks
  (`on: "COORDINATOR"`) aren't supported, see [Limitations](/reference/limitations#not-supported).
</Callout>

## Worker variables

As in Cucumber's parallel mode, every worker has:

| Variable                 | Value                                   |
| ------------------------ | --------------------------------------- |
| `CUCUMBER_WORKER_ID`     | the worker's id, unique in the run      |
| `CUCUMBER_TOTAL_WORKERS` | Vitest's `maxWorkers`                   |
| `CUCUMBER_PARALLEL`      | `"true"`                                |

They're set before your support code loads. Where you read them depends on the mode:

```ts
// Node mode
const worker = process.env.CUCUMBER_WORKER_ID;

// Browser mode and Storybook: a page has no `process`
const worker = import.meta.env.CUCUMBER_WORKER_ID;
```

Support code that runs in both can pick whichever has them:

```ts
const env = import.meta.env.CUCUMBER_WORKER_ID ? import.meta.env : process.env;
```

## Attachments

```ts
Then("I see the receipt", async function (this: CartWorld) {
  this.log("receipt checked");
  this.link("https://example.com/orders/42");
  this.attach(JSON.stringify(this.items), "application/json");
});
```

They're the test's [annotations](/guides/results#attachments). Node mode takes strings, `Buffer`s and
streams; a page takes strings only, so attach binary data as base64 with a `base64:` media type
(`"base64:image/png"`).

## Timeouts

Each step and hook has its own timeout, as in Cucumber:

```ts
When("the report is ready", { timeout: 30_000 }, async function () {
  // …
});
```

Without one, Vitest's: its `testTimeout` for a scenario's steps and hooks, its `hookTimeout` for
`BeforeAll` and `AfterAll` (Vitest's defaults: 5 and 10 seconds in Node.js, 15 and 30 in browser
mode; `0` for none).

- A scenario as a whole has no timeout, unless a [tag](/guides/running#tag-options) with a `timeout`
  gives it one: the whole scenario must then finish in time.
- Cucumber's `setDefaultTimeout` isn't supported: set Vitest's `testTimeout` and `hookTimeout`.
- Fake timers don't change them.
- In Storybook's UI (`storybook dev` and static builds) there's no Vitest, and Storybook has no
  timeout for a play function: steps and hooks have none either, unless a definition sets its own.

## Defining steps

Definitions are recorded while the support code loads. Calling `Given` (or any definition function)
later, e.g. inside a step, throws
`[@lotun/vitest-cucumber] "Given" was called after the support code loaded`.
